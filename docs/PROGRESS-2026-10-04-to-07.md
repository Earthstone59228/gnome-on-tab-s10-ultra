# Progress since the 2026-10-03 snapshot (Oct 4 – Oct 7, 2026)

Status labels: **user-confirmed** (seen working on the tablet), **tested** (checked by script or log, not independently audited), **experimental**, **failed**. Everything here is a personal, single-device port (SM-X926B, firmware X926BXXS9DZG1, kernel 6.1.145).

## 1. Desktop OpenGL and Vulkan now work (Zink over PanVK) — supersedes "OpenGL is broken"

The earlier conclusion that desktop GL was impossible described the stock Arm blob, which exposes only GLES and no desktop Vulkan ICD. A different route works:

```text
OpenGL app -> Mesa Zink -> Vulkan loader -> PanVK (Mesa, kbase backend) -> stock /dev/mali0 -> Mali-G720 MC12
```

* Mesa 26.2.3 PanVK built against the stock kbase UAPI (1.21) is used as a process-local Vulkan driver. No system GPU library and no kernel module is replaced; wrappers select it only for the child process (`experiments/graphics/zink-panvk/launchers/zink-env`).
* Advertised: Vulkan 1.4, OpenGL 4.6 Core and Compatibility, GLES 3.2. **PanVK is experimental and non-conformant**; the version strings are not a conformance claim.
* Checked: 52,771 shader/FBO pixels and a 128-word GLSL 430 compute result matched a software reference with zero mismatches (`experiments/graphics/zink-panvk/tests`).
* **OrcaSlicer 2.4.2** (official aarch64 AppImage): model viewport, resize and 100-layer preview work and are fast (user-confirmed).
* **Blender 5.2.2**: the launcher now selects native Vulkan with a private, compatible OCIO colour config. Viewport shading and shadows work (user-confirmed). A UI-widget glitch remains (below).
* FreeCAD and OpenSCAD launchers were switched to Zink; they are untested on the device.
* gl4es and MobileGL (the Oct 3 experiments) are now retire candidates. `gnome_gbm_shim` and the libhybris Wayland client stack are still required for the compositor and GTK4/Firefox; PanVK does not replace them.

### Open: Blender widget corruption on PanVK
Menu/panel widgets draw with wrong colours after a few workspace switches. Reproduced headlessly against a software reference. Every tested full barrier between consecutive render passes removes it, so it is an execution-ordering hazard between back-to-back passes (likely a missing CSF subqueue sync), not caches or per-draw state. A diagnostic interposer and a minimal fence shim are in `experiments/graphics/panvk-diagnostics/` (mitigation validated in tests, **not deployed**; a real fix belongs in PanVK).

## 2. Hardware video decode (tried, removed)
Hardware decode through the MediaTek video device plus an Android-side conversion step was proven in mpv (VP9/AV1/H.264/HEVC 4K60, bit-exact, roughly half the CPU). Firefox could not use it, and the extra moving parts were judged too clunky, so the stack was removed from the tablet.

## 3. Desktop polish and input (Oct 3–5)
Liquid-glass style OSK and app-menu surfaces, a full on-screen keyboard (F-keys, latching Ctrl/Alt/Super, Fn level), shell haptics (pulses of 40–70 ms work), a file-picker fix, and two touch-extension candidates installed disabled for A/B. These live in the GNOME Shell overlays and extensions that are not all exported to this repository yet.

## 4. Power and sleep
* Overnight drain is a flat ~3 W. gnome-shell uses ~2 % of a core. The cause is Android seeing the screen on with a full wake lock held all night, so it never suspends. An always-on audio silence stream and fork-heavy pollers were also removed (audio bridge on demand, slower polling).
* "Power button" currently only draws a black layer (plus lock); the panel stays powered and nothing sleeps. Powering the panel down through the backlight node posts LCD_OFF, which detaches the pogo keyboard and, with SurfaceFlinger stopped, crash-loops Android's framework (older finding; the keyboard ghost fix made detach survivable, so this is worth re-testing).
* **Deep sleep test, Oct 7: failed (watchdog panic).** Only `s2idle` is available (`mem_sleep` = `[s2idle]`); Android itself suspends fine normally. In a live session, a 10 s `echo mem > /sys/power/state` with the panel left powered wedged inside the MediaTek DRM driver's suspend (`mtk_drm_sys_suspend` -> `mtk_atomic_commit` never returned) because the compositor, not HWC, owns the display pipeline. The software watchdog then panicked the kernel as designed. Details and next idea: `experiments/power/README.md`.

## 5. Safety/process notes carried forward
Audit risky device changes with a fresh reviewer; verify config keys and APIs against the deployed binary, not by analogy; never touch the panel power during a session; keep a backup beside every deployed file.
